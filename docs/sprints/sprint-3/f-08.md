## 1. Scope and ownership

F-08 gives a Survey Owner charts for their own survey, a paginated browser for identified responses, and CSV/JSON downloads. The authenticated owner can inspect raw responses and respondent identity only for an identified survey they own. Anonymous surveys use aggregate charts and aggregate-only exports through F-08: no raw response, raw text, respondent identity, response ID, claim, or answer-to-person link appears in anonymous exports or the response browser.

| Requirement | F-08 behavior |
|---|---|
| FR-10 | Presents the owner’s aggregate summary as type-appropriate charts; F-04 remains the source of aggregate counts and statistics. |
| FR-13 | Owner downloads CSV or JSON for their own survey. Identified mode exports raw responses; anonymous mode exports aggregates only. |
| FR-16 | Owner browses individual response content and respondent identity only for their own identified survey. |
| BR-11 | Aggregates and anonymous exports contain no respondent identity. Identified raw export/browsing is the sole exception and is restricted to the owning Survey Owner. |
| FR-11 / BR-10 | F-05 owns anonymous unlinkability and response-independent claims. F-08 must not add or infer a claim-to-response link. |
| FR-12 | Use all nine question types in the current F-06 catalog and its typed answer representation. |

F-08 does not add survey, question, answer, response, or claim persistence; change submission; modify claim retention; or expose response data to respondents through new routes. Exports are generated on demand and do not write application records or create retained export files. Existing submission and receipt behavior remains under F-05/F-06/#72.

### 1.1 Recorded source clarification

The SRS BR-11 sentence could be read to prohibit identity fields from every export, while SRS §5.1 explicitly permits identity in an identified raw export to its owner. This contract adopts the more specific §5.1 rule and narrows BR-11 wording: identity is allowed only in the owner’s identified raw export and identified response browser; it is never present in aggregates or anonymous output. Issue #63 further narrows the older SDS §7.2 anonymous-export wording: F-08 anonymous exports are aggregate-only and do not include the unlinked text that the F-05 summary may show. The SRS and SDS wording is amended in the same change as this contract, before behavior changes.

| Decision | Reason | Effect |
|---|---|---|
| Include respondent identity in an identified raw export only for its owner | Resolves the general BR-11 sentence against the explicit SRS §5.1 access table | Raw export is mode-specific; aggregate data never carries identity |
| Anonymous export is aggregate-only, without unlinked text | Follows Issue #63’s explicit acceptance criterion | F-05 summary behavior is unchanged; anonymous export is stricter |
| Keep CSV as the only runtime deliverable in this Issue #63 slice | Issue #63’s two-stage scope | JSON, charts, and response browsing remain planned and are not claimed done |

Aggregate-only output prevents explicit identity fields and response links; it does not prevent inference from sparse counts plus outside knowledge. This issue does not add a minimum-cell threshold or statistical noise because existing summary contracts expose exact counts. If the product must protect against inference, record and review that policy before implementing exports.

## 2. Roles, permissions, and API behavior

Every F-08 endpoint requires a valid authenticated JWT. Role and ownership checks happen before reading nested response/answer data. The owner must own the requested survey. Do not return survey, response, answer, claimant, or identity data in an authorization error.

| Surface | Caller | Result |
|---|---|---|
| `GET /api/surveys/:id/summary` | Owner of the survey | Existing aggregate summary DTO, extended only as required by §3.1; no respondent or response identifiers |
| `GET /api/surveys/:id/responses` | Owner of an identified survey | Paginated identified raw responses, including respondent details and typed answers |
| `GET /api/surveys/:id/export?format=csv` | Owner of own survey | CSV download using the mode-specific schema in §4 |
| `GET /api/surveys/:id/export?format=json` | Owner of own survey | JSON download using the mode-specific schema in §5 |
| Response browser/export, wrong role | Authenticated non-owner role | `403 FORBIDDEN_ROLE`; no private data |
| Response browser/export, another owner’s survey | Authenticated Survey Owner | `403 FORBIDDEN_OWNERSHIP`; no private data |
| Anonymous response browser | Owner of an anonymous survey | `403 ANONYMOUS_RAW_RESPONSES_DISABLED`; no response or answer data |
| Any F-08 surface | Missing, malformed, expired, or revoked token | `401` using the existing auth error code; no private data |
| Any F-08 surface | Unknown survey | `404 NOT_FOUND` |
| Export | Missing/unsupported `format`; malformed pagination input | `400 VALIDATION_ERROR`; no private data |

The summary endpoint remains the chart data source; no separate chart endpoint is added. It keeps the F-06 question order and typed summary shapes. The response browser uses keyset pagination ordered by `submittedAt ASC, responseId ASC` and the existing success envelope:

```http
GET /api/surveys/:id/responses?limit=25
GET /api/surveys/:id/responses?limit=25&cursor=<nextCursor>
```

`limit` is optional, defaults to 25, and must be an integer from 1 through 100. `cursor` is omitted for the first page and otherwise is the exact `nextCursor` string returned by the previous page. The cursor is an opaque base64url encoding of the ordering tuple `{ "submittedAt": "<ISO-8601 UTC>", "responseId": "<UUID>" }`; clients must not construct or interpret it. The server applies a strict tuple-after comparison, fetches up to `limit + 1` rows, and returns at most `limit` items.

The successful response is `200` with `{ "success": true, "data": { "items": [...], "nextCursor": "<opaque cursor>" } }`. `data.items` contains the identified response items described below. `data.nextCursor` is the cursor for the last returned item only when an additional row exists; otherwise it is `null`, including on an empty result. A client shows **Next** only when `nextCursor` is non-null, sends it as the next request’s `cursor`, and retains the cursor used for each page to support **Previous**. Every page repeats authentication, role, ownership, and identified-mode checks. A malformed cursor or a limit outside 1–100 returns `400 VALIDATION_ERROR` before response data is read.

Identified response items contain `responseId`, `submittedAt`, `respondent` (`id`, `fullName`, `email`), and `answers`. Each answer contains `questionId`, `order`, `prompt`, `questionType`, and `value` in the typed representation defined in §3.2. Unanswered optional questions appear with `value: null`. The browser orders answers by `question.orderIndex ASC, question.id ASC` and presents pending, empty, page navigation, and safe error states. It does not display anonymous responses or claims.

Use the existing error envelope and stable codes. `401`, `403`, `404`, and `400` responses contain no private survey or response fields. A failed read does not mutate survey, response, answer, or claim data.

## 3. Data and analytics

### 3.1 Chart definitions

The charts are rendered from the owner summary DTO, never from respondent identity or claim data. Counts include all submitted responses applicable to the question. An unanswered optional question does not count as an answer. Each chart displays its question’s `answeredCount` and the survey’s `totalResponses` so the denominator is visible.

| Question type | Chart and deterministic order | Count and percentage |
|---|---|---|
| `SINGLE_CHOICE` | One bar per configured option, in option order; zero-count options remain visible | Count per selected option; percentage is `count / answeredCount * 100`, rounded to two decimals |
| `MULTI_CHOICE` | One bar per configured option, in option order; zero-count options remain visible | Count per selection; percentage uses `answeredCount` as denominator, so totals may exceed 100% |
| `YES_NO` | Two bars in `Yes`, `No` order | Count and percentage among answered questions |
| `LIKERT` | Five bars in the F-06 label order: Strongly disagree, Disagree, Neither agree nor disagree, Agree, Strongly agree | Count and percentage among answered questions |
| `RATING` | Five bars for integer values 1–5, including zero-count buckets | Count and percentage among answered questions; show F-06 count/average/min/max stats |
| `INTEGER` | One bar per observed integer, numeric ascending; no invented ranges or bins | Exact-value count; show F-06 count/average/min/max stats |
| `DATE` | One bar per observed date, ascending `YYYY-MM-DD` | Count per date; no time-zone conversion |
| `SHORT_TEXT`, `LONG_TEXT` | No distribution chart | Show answered count only in anonymous mode; identified summary may keep F-06’s unlinked text display |

If `answeredCount` is zero, show an empty-state message and no `NaN`/infinite percentages; bucketed questions keep their configured zero-count buckets. Multi-choice percentages can sum above 100% by definition. The chart must not infer identities from aggregate values or add cross-question joins.

### 3.2 Answer value shapes

Use the current F-06 question and answer types; do not add a migration for F-08. The browser and identified JSON use these values:

| Type | `value` |
|---|---|
| `SINGLE_CHOICE`, `YES_NO`, `LIKERT` | `{ optionId, label }` |
| `MULTI_CHOICE` | Array of `{ optionId, label }`, ordered by question option order |
| `SHORT_TEXT`, `LONG_TEXT` | String, preserving stored text |
| `RATING`, `INTEGER` | JSON number |
| `DATE` | Date-only `YYYY-MM-DD` string |
| Unanswered optional question | `null` |

The current supported catalog is `SINGLE_CHOICE`, `MULTI_CHOICE`, `SHORT_TEXT`, `LONG_TEXT`, `YES_NO`, `LIKERT`, `RATING`, `INTEGER`, and `DATE`. A future type requires an F-06/F-08 contract update before it can be exported; no type is silently omitted.

## 4. CSV schemas and serialization

CSV is UTF-8 without a byte-order mark, uses CRLF record terminators and RFC 4180 quoting, and has one header row even when there are no response rows. A field containing comma, double quote, CR, or LF is enclosed in double quotes; an internal double quote is doubled. Other Unicode is preserved as UTF-8. CSV column order and row order are fixed. Files are named `survey-<surveyId>-identified.csv` or `survey-<surveyId>-aggregate.csv`; no survey title or user input is used in the filename.

For a text cell whose first non-space/tab character is `=`, `+`, `-`, or `@`, or whose first character is a tab, CR, or LF, prefix an apostrophe before CSV quoting to prevent spreadsheet formula execution. Apply this only to text cells (including prompts, labels, names, emails, and text answers), not numeric or date cells. Persisted values are unchanged. Tests must verify this transform and all CSV escaping cases.

### 4.1 Identified raw CSV

The exact header is:

```text
survey_id,survey_title,response_id,submitted_at,respondent_id,respondent_full_name,respondent_email,question_id,question_order,question_prompt,question_type,text_value,number_value,date_value,selected_options_json
```

There is one row for every `(response, survey question)` pair, including an unanswered optional question. Rows sort by `submitted_at ASC, response_id ASC`, then `question_order ASC, question_id ASC`. Survey and respondent fields repeat per row. `submitted_at` is ISO 8601 UTC; `question_order` is the stored zero-based order index; `question_type` is the exact enum name. `text_value` is populated only for short/long text; `number_value` only for rating/integer; `date_value` only for date; all are empty for other types or unanswered questions. `selected_options_json` is a compact JSON array of `{ "optionId": "…", "label": "…" }` in option order for choice, yes/no and Likert answers; it is `[]` for unanswered option questions and empty for non-option question types. Empty typed values use empty cells, not the strings `null` or `undefined`.

A survey with no responses produces the header only. This schema includes the respondent identity because it is a raw export of an identified survey; it is unavailable for an anonymous survey.

### 4.2 Anonymous aggregate CSV

The exact header is:

```text
survey_id,survey_title,question_id,question_order,question_prompt,question_type,metric,bucket_value,count,answered_count,total_responses,percentage,average,minimum,maximum
```

This export has one row for each aggregate bucket defined in §3.1. Choice options and rating values include zero-count buckets; integer and date types contain one row per observed value, sorted numerically or by date. For a text question, use one row with `metric=answered_count`, empty `bucket_value`, and `count=answered_count`; never export text answers. When an integer or date question has no answers, emit one zero-count row with an empty bucket. When a text question has no answers, emit its zero-count row. `average`, `minimum`, and `maximum` follow F-06 statistics and are empty where not applicable or when no numeric answer exists. `total_responses` repeats the survey total. Percentage follows the rules below.

For choice and rating buckets, `percentage` is `count / answered_count * 100`, rounded to two decimals, as in §3.1. It is empty when `answered_count=0`. For integer and date bucket rows, and the text-question `answered_count` row, `percentage` is always empty; these types have no percentage distribution in the F-06 summary contract. Number statistics repeat on each applicable integer/rating bucket row and remain empty for other types.

The anonymous CSV may contain survey/question IDs, prompts, configured option labels, and aggregate values. It must not contain a respondent/user/claim ID, response ID, raw text answer, per-response timestamp, or any field that links an answer to a person or response. No respondent identity is included in aggregate rows for an identified survey either.

## 5. JSON schemas

JSON downloads use UTF-8, `application/json; charset=utf-8`, and `schemaVersion: 1`. Object property order is not significant; arrays use the same deterministic question, response, and option orders as CSV. Unknown properties are not added to the v1 contract without a contract revision.

### 5.1 Identified raw JSON

```json
{
  "schemaVersion": 1,
  "survey": { "id": "<surveyId>", "title": "<title>", "mode": "IDENTIFIED" },
  "responses": [
    {
      "responseId": "<responseId>",
      "submittedAt": "<ISO-8601 UTC>",
      "respondent": { "id": "<userId>", "fullName": "<name>", "email": "<email>" },
      "answers": [
        { "questionId": "<questionId>", "order": 0, "prompt": "<prompt>", "questionType": "<enum>", "value": "<typed value or null>" }
      ]
    }
  ]
}
```

`answers` contains one item per survey question, ordered by question order; optional unanswered values are `null`. Typed values use §3.2. `responses` sort by submitted timestamp ascending then response ID ascending. Identified JSON is specified for full F-08 but is not part of the CSV-only runtime slice in Issue #63.

### 5.2 Anonymous aggregate JSON

```json
{
  "schemaVersion": 1,
  "survey": { "id": "<surveyId>", "title": "<title>", "mode": "ANONYMOUS" },
  "totalResponses": 0,
  "questions": [
    {
      "questionId": "<questionId>", "order": 0,
      "prompt": "<prompt>", "questionType": "<enum>", "answeredCount": 0,
      "options": [], "ratingDistribution": [], "numberStats": null,
      "integerCounts": [], "dateCounts": []
    }
  ]
}
```

Only properties relevant to a type are present. Choice types use `options: [{label,count,percentage}]` in option order; rating uses all five `ratingDistribution: [{value,count}]` buckets and F-06 `numberStats`; integer uses ascending exact `integerCounts: [{value,count}]` and `numberStats`; date uses ascending `dateCounts: [{date,count}]`; text uses `answeredCount` only. Empty arrays are used for a type’s empty distribution and `numberStats` is `null` when no numeric answer exists. This schema never includes `textAnswers`, raw answers, respondent or response identifiers, claims, or response-to-person links. Anonymous JSON remains planned in this issue slice.

With no responses, identified JSON returns `responses: []` and anonymous JSON returns `totalResponses: 0`; every configured question remains present with `answeredCount: 0`, zero-count configured choice/rating buckets, empty integer/date distributions, and `numberStats: null`. An empty survey has no response entries and, in anonymous JSON, `questions: []`. These are successful `200` exports, not errors.

## 6. User interface states

The owner’s results page shows the aggregate summary and type-appropriate charts. It offers **Browse responses** only for an identified survey, and CSV/JSON export controls for either mode. Mode and export labels make clear that anonymous downloads contain aggregates only. The raw browser displays respondent identity and typed answer values only for an identified survey. Anonymous mode never renders a response row, identity, raw text, receipt, response ID, or claim information.

The page provides loading, no-responses/empty-chart, pagination, download-in-progress, and safe error states. A denied or failed request clears protected content from that view. Respondent-facing pages gain no F-08 browsing or export controls. Controls are not a security boundary; server authorization is required for every request.

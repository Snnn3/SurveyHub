## 1. Scope and ownership

F-05 lets a Survey Owner choose whether a draft collects identified or anonymous responses. Identified remains the default. F-05 supplies a small policy module for #72 to use when it creates a response and a response-independent claim. It also defines the anonymous receipt and summary boundary. F-05 does not implement claim/response transaction orchestration, eligibility, scheduling, expanded question types, exports, or raw response browsing.

| Requirement | F-05 application |
|---|---|
| FR-09 | Identified receipts retain the Sprint 1 behavior. Anonymous receipts are opaque, metadata-only confirmations; they contain no answer or respondent fields. |
| FR-11 | A draft can select `IDENTIFIED` or `ANONYMOUS`; anonymous responses contain no respondent link, while a separate claim prevents a repeat submission. |
| BR-05 | Identified receipts remain available only to their respondent. Anonymous receipts are retrieved by opaque response UUID by an authenticated RESPONDENT and disclose only survey/response IDs, submission time, and mode; possession of the reference is the authorization for this limited metadata. |
| BR-10 | Anonymous response rows have `respondentId = NULL`; a claim links only survey and claimant and has no response ID, response foreign key, timestamp, or reverse response lookup. |
| NFR-PRIV-01 | Anonymous summary and receipt DTOs contain no respondent identity or answer-to-person association. Verify both API shape and persisted null respondent link. |

`ResponseClaim.userId` records that a user has claimed a survey to enforce one submission. It does not identify which response belongs to that user. `ResponseClaim` must not gain a response identifier, response relation, timestamp, or query path that maps a claim to a response. Claims are retained as long as needed for duplicate prevention.

### 1.1 Receipt and history decision

FR-09's full identified receipt conflicts with BR-10 if applied to anonymous mode. Keep the existing identified receipt unchanged. An anonymous receipt has exactly `responseId`, `surveyId`, `submittedAt`, `mode: ANONYMOUS`, and `answers: []`; it is a confirmation reference, not an answer archive. Its UUID is an opaque bearer reference. The existing endpoint remains authenticated and RESPONDENT-only, but does not compare the current user with a claim. Anyone holding a valid reference and a respondent account may see only those metadata values. The survey list may report `hasSubmitted`; it must not expose an anonymous response ID or associate a claim with a response.

This limited receipt preserves retrieval of a persisted confirmation without creating a respondent-to-response link. It does not claim protection against a privileged database operator correlating transaction logs or external observations.

## 2. Configuration API and persistence

`POST /api/surveys` and `PUT /api/surveys/:id` accept an optional `mode` equal to `IDENTIFIED` or `ANONYMOUS`. Omission on create means `IDENTIFIED`; omission on update preserves the stored value. The `GET /api/surveys/:id` owner detail, owner list, and successful create/update response include `mode`. The form response includes `mode` so the respondent sees the correct privacy notice. Existing callers that omit the field continue to work.

Only the owner may choose or change mode, and only while the survey is `DRAFT`. A non-owner receives `403 FORBIDDEN_OWNERSHIP`; an authenticated user without the owner role receives `403 FORBIDDEN_ROLE`; a mode value outside the enum receives `400 VALIDATION_ERROR`; an update to a non-draft survey retains `400 SURVEY_NOT_EDITABLE`. Rejection leaves the survey mode and structure unchanged.

The owner editor exposes a labeled mode control on create and edit. It defaults to Identified, explains the anonymous receipt/claim behavior, and reloads the persisted mode when a draft is opened. Saving mode uses the existing draft API. No separate endpoint or settings table is added.

## 3. Data and public policy module

Reuse `Survey.mode`, nullable `SurveyResponse.respondentId`, and `ResponseClaim(surveyId,userId)`. The current schema gap is `ResponseClaim.createdAt`, which conflicts with this contract's no-timestamp rule. Update the SDS before migration, then remove the column and Prisma field without deleting claim rows or changing the existing unique/index constraints.

The isolated server policy module exports a small, framework-independent function:

```ts
getSubmissionIdentity(mode, userId) => {
  respondentId: mode === 'IDENTIFIED' ? userId : null,
  claimUserId: userId,
}
```

`#72` may use that result inside its transaction. The module does not accept or return a response ID, Prisma transaction, database delegate, answer, or response lookup. It does not perform writes. Anonymous receipt shaping likewise returns only `responseId`, `surveyId`, `submittedAt`, `mode: ANONYMOUS`, and an empty answers array.

## 4. User-visible behavior and access

- The owner can see and save the mode on a draft they own. Published surveys keep their stored mode; mode cannot be edited after publication.
- Until #72 integrates transaction handling, publishing an anonymous draft or submitting to an already-published anonymous survey returns `400 ANONYMOUS_MODE_NOT_READY` without changing data. #72 removes this temporary gate as part of enabling the integrated anonymous flow.
- The form identifies anonymous mode and explains that submission support is pending until #72 is integrated; it does not imply the submission succeeded.
- After submission, identified mode shows the existing response ID, timestamp, and answer receipt. Anonymous mode shows the opaque reference and timestamp, omits answers, and tells the respondent to keep the reference.
- Anonymous owner summaries may include aggregates and unlinked text answers but never names, emails, user IDs, response IDs, or claim-to-response information.
- Existing role and ownership checks remain server-side. Error bodies contain no private survey, response, or answer data.

## 5. Acceptance criteria

| ID | Acceptance criterion |
|---|---|
| **AC-F05-01** | The mode API accepts only `IDENTIFIED` and `ANONYMOUS`; create defaults to `IDENTIFIED`, update omission preserves the saved mode, and owner detail/list responses return it. |
| **AC-F05-02** | The owner editor lets an owner select either mode on a draft, saves it, and reloads the selected mode. New drafts start identified. |

## 7. Boundaries and definition of done

- F-05 owns this contract, the owner mode control, validation/persistence surface, isolated privacy policy module, receipt-shape boundary outside `response.service.ts`, migration, and F-05 tests.
- #72 exclusively owns `server/src/services/response.service.ts`, submission orchestration, claim writes, and transaction/concurrency integration. It consumes the helper without moving its seam.
- #61 owns eligibility and scheduled-close behavior. #67 owns F-06 question types. Keep their modules and settings isolated.
- No schema change may drop response, claim, or answer records. The only planned migration change is dropping `response_claims.created_at` after the contract/SDS change.
- The F-05 PR targets `sprint-2-staging`, links #60, includes actual checks, and is not merged without teammate approval and required checks.
- #60 verifies the owner mode editor, anonymous form, and metadata-only confirmation UI. #72 owns real anonymous submission, transaction/concurrency, and persisted receipt integration; #60 must not claim those results.

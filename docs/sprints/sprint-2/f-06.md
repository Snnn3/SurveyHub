## 2. Shared question catalog and configuration

Question configuration uses the existing authoring names: prompt, questionType, isRequired, orderIndex, and options. Type-specific fields are minSelections/maxSelections for multi-choice and numberMin/numberMax for integer. Unused type-specific fields are omitted from requests and stored as null where the existing schema requires a value.

Option labels are trimmed, non-empty, at most 200 characters, and unique case-insensitively within a question. User-configured choice questions retain the existing maximum of 20 options. Persisted and returned options include id, label, and orderIndex.

| Type | Author configuration | Respondent value | Persistence |
|---|---|---|---|
| SINGLE_CHOICE (Sprint 1) | At least 2 configured options; retain current limits and behavior. | Exactly one selectedOptionIds entry. | One AnswerOption relation. |
| SHORT_TEXT (Sprint 1) | No options or F-06 configuration. | textValue; trim before validation and persistence; maximum 2,000 characters. | Answer.textValue. |
| MULTI_CHOICE | 2–20 configured options; minSelections and maxSelections are required integers; 1 ≤ minSelections ≤ maxSelections ≤ option count. | A distinct list of question-owned selectedOptionIds. When present, its length is within the configured inclusive bounds. | One Answer row and one AnswerOption relation per selected option. |
| LONG_TEXT | No options or numeric configuration. | textValue, trimmed; maximum 10,000 characters. | Answer.textValue. |
| YES_NO | No owner-editable options. The server supplies exactly Yes then No. | Exactly one selectedOptionIds entry for one of the two question-owned fixed options. | One AnswerOption relation. |
| LIKERT | No owner-editable options. The server supplies the ordered labels Strongly disagree, Disagree, Neither agree nor disagree, Agree, Strongly agree. | Exactly one selectedOptionIds entry for one of the five question-owned fixed options. | One AnswerOption relation. |
| RATING | Fixed scale 1 through 5; no options or configurable bounds. | numberValue is an integer from 1 through 5. | Answer.numberValue. |
| INTEGER | Optional numberMin and numberMax are inclusive integer bounds. Each may be absent; if both are present, numberMin ≤ numberMax. | numberValue is a whole number and respects every configured bound. | Answer.numberValue. |
| DATE | No options or numeric configuration. | dateValue is a real calendar date in YYYY-MM-DD form, with no time or zone. | Answer.dateValue in the existing PostgreSQL DATE column. |

A required question must have a valid value. An optional unanswered question is omitted from the answers array. If an optional text value is blank after trimming, it is treated as unanswered. If an answer is submitted, it must satisfy the same type-specific value and configured bounds as a required answer. A configured multi-choice minimum applies whenever an answer is supplied.

When creating or updating a draft, validate F-06 type-specific configuration before writing: reject fields that do not apply to the selected type, malformed or missing multi-choice bounds, contradictory integer bounds, invalid option labels, and any non-canonical fixed-scale configuration with 400 VALIDATION_ERROR. Publishing revalidates the complete survey, including non-empty prompts, question/option counts, type configuration, and existing prompt/option limits; an invalid structure returns 400 INVALID_QUESTION_STRUCTURE.

## 3. DTOs and API shapes

All endpoints use the existing JSON envelope from the SRS. Request objects remain strict: unknown properties are rejected. IDs are UUID strings. Questions and options are ordered by orderIndex, then id as the stable tie-breaker already used by the API.

### 3.1 Authoring request

POST /api/surveys and PUT /api/surveys/:id retain their existing full-survey request. Each question adds only the configuration fields that apply to its type.

    {
      "title": "Course feedback",
      "description": null,
      "questions": [
        {
          "prompt": "Which topics were useful?",
          "questionType": "MULTI_CHOICE",
          "isRequired": true,
          "options": [{"label": "Testing"}, {"label": "Design"}, {"label": "Teamwork"}],
          "minSelections": 1,
          "maxSelections": 2
        },
        {
          "prompt": "What should change?",
          "questionType": "LONG_TEXT",
          "isRequired": false,
          "options": []
        },
        {
          "prompt": "Would you recommend the course?",
          "questionType": "YES_NO",
          "isRequired": true
        },
        {
          "prompt": "Rate the course",
          "questionType": "RATING",
          "isRequired": true
        },
        {
          "prompt": "How many labs did you attend?",
          "questionType": "INTEGER",
          "isRequired": false,
          "numberMin": 0,
          "numberMax": 12
        },
        {
          "prompt": "What date did you attend?",
          "questionType": "DATE",
          "isRequired": false
        }
      ]
    }

This example is illustrative and omits a LIKERT question. For YES_NO and LIKERT, clients send the question type and no editable options; the server creates the canonical options. Existing SINGLE_CHOICE requests and SHORT_TEXT requests remain valid without any F-06 fields.

The owner-only `GET /api/surveys/:id` detail and the successful `PUT /api/surveys/:id` response use the existing F-02 full-survey shape. Their questions and options are ordered by `orderIndex`, then `id`. F-06 detail includes `minSelections`/`maxSelections` for MULTI_CHOICE, `numberMin`/`numberMax` for INTEGER, and the canonical ordered options for YES_NO and LIKERT. Reloading the editor returns the last successfully saved values and order; other types add no configuration fields.

### 3.2 Respondent form

GET /api/surveys/:id/form remains respondent-only and returns the existing survey metadata plus ordered questions. Each question retains id, prompt, questionType, isRequired, orderIndex, and options. It additionally returns minSelections/maxSelections for MULTI_CHOICE or numberMin/numberMax for INTEGER when configured. Fixed YES_NO and LIKERT options appear as ordinary ordered options with server IDs. The form endpoint does not return answers, respondents, or summary data.

The form question DTO uses UUID strings for id and option ids, strings for prompt/labels, the QuestionType enum for questionType, booleans for isRequired, integers for orderIndex and configured bounds, and an ordered options array of {id, label, orderIndex}. Unused type-specific bounds are omitted. The response renders these fields without adding persisted answers.

### 3.3 User interface controls

| Type | Owner editor | Respondent form |
|---|---|---|
| MULTI_CHOICE | Editable ordered option list plus required integer min/max fields and relationship validation. | Labeled checkbox group; show selection feedback and enforce min/max before submit. |
| LONG_TEXT | Distinct type choice from SHORT_TEXT; no options or bounds. | Labeled textarea with a 10,000-character limit and required/trimmed validation feedback. |
| YES_NO | Fixed Yes/No options displayed read-only in that order. | Labeled radio group with Yes then No. |
| LIKERT | Fixed five labels displayed read-only in the contracted order. | Labeled radio group in the same order. |
| RATING | Fixed scale with no author-configurable range. | Labeled single-select scale containing only integers 1 through 5. |
| INTEGER | Optional integer minimum and maximum fields. | Labeled numeric input with step 1 and configured min/max when present. |
| DATE | No additional question configuration. | Labeled calendar-date input; send its unchanged YYYY-MM-DD value. |

All controls use visible labels and keyboard navigation, consistent with Shared UI states and Accessibility and usability conventions in the [system design](../../system-sds.md). The server remains authoritative. The owner summary presentation renders the type-specific aggregates in §3.5 and does not attach answer rows to respondent identities. It shows a loading skeleton while fetching, a safe error banner on API failure, a 403 access-denied view without summary data, an empty state when there are no responses, and question rows for partially answered surveys without dividing by zero.

The owner editor shows a pending state while loading `GET /api/surveys/:id` and while saving with `PUT /api/surveys/:id`; it prevents another save while that request is pending. A successful save replaces the saved baseline with the returned detail. A `400 VALIDATION_ERROR` shows safe field/question feedback and keeps the edited values in the editor; the last valid persisted draft remains unchanged. A server error or network failure shows safe feedback and keeps the edited values. If the save outcome is unknown, a later reload fetches the current persisted detail so the editor can reconcile it without discarding local edits first.

### 3.4 Submission request and receipt

POST /api/surveys/:id/responses keeps the existing answers array and uses exactly one value field for each submitted answer:

    {
      "answers": [
        {"questionId": "<uuid>", "selectedOptionIds": ["<option-uuid>", "<option-uuid>"]},
        {"questionId": "<uuid>", "textValue": "A detailed comment"},
        {"questionId": "<uuid>", "numberValue": 4},
        {"questionId": "<uuid>", "dateValue": "2026-11-20"}
      ]
    }

selectedOptionIds is the existing Sprint 1 field and remains an array: SINGLE_CHOICE, YES_NO, and LIKERT require exactly one distinct ID; MULTI_CHOICE requires the configured number of distinct IDs. LONG_TEXT uses textValue, RATING and INTEGER use numberValue, and DATE uses dateValue. Do not accept mixed value fields, duplicate question IDs, duplicate option IDs, options from another question, fractional numeric values, or timestamp/date-time strings.

Successful submission remains HTTP 201 with responseId, surveyId, submittedAt as an ISO 8601 UTC timestamp, and the existing success message. GET /api/surveys/:id/responses/:responseId remains the respondent's own receipt. For Sprint 1 types, its answer entries retain the existing questionId, prompt, questionType, textValue, selectedOptionIds, and selectedOptions fields and their current values. F-06 adds numberValue for RATING and INTEGER, and dateValue for DATE; choice types continue to use selectedOptionIds and selectedOptions. Date receipt values are serialized as YYYY-MM-DD, never as an instant. No receipt change may expose another respondent's data.

While the submission request is pending, the respondent form shows progress and prevents a second submit. For `400 INVALID_ANSWER` or `400 MISSING_REQUIRED_QUESTIONS`, it shows safe question-level feedback and preserves every entered answer so the respondent can correct it. Any other unsuccessful response, server error, or network failure keeps the form and all entered values visible with a safe error/retry message. Only a confirmed `201` transitions to the receipt; do not clear answers before that response.

### 3.5 Owner summary DTO

GET /api/surveys/:id/summary remains owner-only. The existing top-level surveyId, title, description, status, mode, totalResponses, createdAt, and questions fields stay stable. Every question keeps questionId, prompt, questionType, and answeredCount. The type-specific fields are:

| Type group | Summary fields |
|---|---|
| SINGLE_CHOICE, MULTI_CHOICE, YES_NO, LIKERT | options: optionId, label, count, percentage. Percentage is count divided by this question's answeredCount, rounded to two decimals; when answeredCount is zero, percentage is 0. Multi-choice percentages may sum above 100%. |
| SHORT_TEXT, LONG_TEXT | textAnswers: trimmed non-empty strings with no respondent or response identifiers. |
| RATING | numberStats: count, average, min, max; ratingDistribution: buckets for each integer from 1 through 5, including zero-count buckets. |
| INTEGER | numberStats: count, average, min, max. |
| DATE | dateCounts: date and count entries sorted by date ascending. |

For numberStats, count equals answeredCount; average is rounded to two decimal places and min/max are the observed submitted values. When count is zero, average, min, and max are null. dateCounts is empty when no answer exists. Choice options still appear with zero counts. optionId is a UUID string, label is a string, count is an integer, and percentage is a JSON number. numberStats has integer count, numeric-or-null average, and integer-or-null min/max. ratingDistribution is an ordered array of integer value/count pairs; dateCounts is an array of YYYY-MM-DD date/count pairs. textAnswers is an array of strings. The summary never includes respondent name, email, user id, response id, or a response-to-person link. These rules apply to both identified and anonymous surveys; anonymous mode's additional claim/receipt restrictions are governed by F-05.

## 4. Validation, errors, and persistence boundaries

The API continues to return the standard error envelope: success=false and error with stable code, safe message, and optional details. Never include SQL, stack traces, submitted secrets, or another respondent's data.

| Condition | HTTP and code | Observable details |
|---|---|---|
| Malformed authoring field or unknown request property | 400 VALIDATION_ERROR | Existing field-level validation details; no write. |
| Invalid F-06 draft configuration submitted by the owner | 400 VALIDATION_ERROR | Safe field/question details; the last valid draft remains unchanged. |
| Invalid question configuration at publish | 400 INVALID_QUESTION_STRUCTURE | Safe field/question details; publish does not occur. |
| Wrong answer field, wrong value type, unknown question, duplicate question/option, foreign option, invalid bound, invalid date, or over-limit text | 400 INVALID_ANSWER | Safe field-level details; no response, claim, or answer is written. |
| Required answer missing after considering submitted answers | 400 MISSING_REQUIRED_QUESTIONS | questionIds contains every missing required question; no response, claim, or answer is written. |
| Respondent calls owner authoring or summary endpoint | 403 FORBIDDEN_ROLE | Error only; no survey/summary data. |
| Non-owner reads or mutates another owner's survey/summary | 403 FORBIDDEN_OWNERSHIP | Error only; no survey/summary data. |
| Unknown survey identifier | 404 NOT_FOUND | No private record data. Unknown question and option identifiers in a submitted answer return 400 INVALID_ANSWER as specified above. |
| Survey is not accepting responses | 400 SURVEY_NOT_ACCEPTING_RESPONSES | Existing F-03 behavior. |

Required text values are checked after trimming. SHORT_TEXT retains the 2,000-character limit; LONG_TEXT is limited to 10,000 characters. Numeric inputs must be JSON numbers that are finite integers; bounds are inclusive. A date must match YYYY-MM-DD and represent a valid Gregorian calendar date (including leap-year rules). It is stored and returned as a date-only value without local-time conversion.

The current schema at baseline ac2ae8f already contains the nine QuestionType enum values, minSelections, maxSelections, numberMin, numberMax, Answer.textValue, Answer.numberValue, Answer.dateValue mapped to PostgreSQL DATE, and AnswerOption for selected choices. The contract therefore expects no schema migration. Before implementation, if analysis finds these fields differ on the current staging head or cannot represent the contract, pause that behavior change, update the SDS and issue #9 with the proposed schema/migration plan, and get review first. Do not add respondent identity to F-06 summary DTOs.

## 5. Authorization and cross-lane ownership

| Surface | Caller | Boundary |
|---|---|---|
| Create, edit, publish a draft | Authenticated SURVEY_OWNER | The owner can change only their own DRAFT survey. Existing published-survey immutability and lifecycle errors remain in force. |
| Respondent form, submit, own receipt | Authenticated RESPONDENT | Role and survey lifecycle/eligibility/deadline policies are enforced server-side. |
| Summary | Authenticated SURVEY_OWNER | Owner must own the survey; authorize before querying nested answer data. No private summary fields are returned on denial. |

Each implementation lane owns only the files and behavior assigned by its issue. These are the shared seams:

| Issue | Contracted seam and ownership |
|---|---|
| #60 | F-05 anonymous configuration and response-independent claim/privacy policy. F-06 passes typed validated answers; it does not add identity to answers or summary output. |
| #61 | Owns both F-07 eligibility and scheduled-close configuration/policies plus isolated decision helpers; it has no response/claim/answer write responsibility. The former #62 deadline-helper lane was consolidated into this issue. |
| #67 | Owns the complete seven-type F-06 implementation: question-structure and answer validation, type-aware summary API, owner editor, respondent form, and owner summary UI. Validation accepts question definitions and submitted answer DTOs, returns normalized typed answers or the contract error, and performs no database writes. Summary serialization follows §3.5 and authorizes the owner before reading aggregate answer data. The former #68–#70 lanes were consolidated into this issue. |
| #72 | Sole owner of response.service.ts and submission transaction. It loads current question definitions, calls #67 validation, composes the #60/#61 policy decisions inside the transaction, and persists the normalized typed values only after every gate accepts. Rejection leaves no response, claim, or answer. |

The #60 and #61 helper contracts remain in their own F-05/F-07 contract documents. This F-06 contract defines only their integration boundary with #72; it does not redefine their policy inputs, outputs, or user settings.

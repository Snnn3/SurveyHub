## 2. Contract F-01: Authentication, Session and RBAC

### 2.1 Scope and linked requirements

- **Requirements:** FR-01, FR-02
- **NFRs:** NFR-SEC-01, NFR-SEC-02, NFR-SEC-03, NFR-SEC-04
- **Feature:** F-01
- **Dependencies:** none
- **Sprint:** 1

### 2.2 Behaviour

- A seeded user logs in with email and password.
- The server normalizes the email (trim, lowercase), verifies the bcrypt hash and returns a JWT.
- The token contains `sub`, `role` and `ver` (token version) and expires after 8 hours.
- Every protected request verifies the token, loads the user and compares `ver`.
- Logout increments `tokenVersion`, revoking every existing token for that account.
- `GET /api/auth/me` returns the current identity and role.
- Passwords are hashed with bcrypt cost 10. No endpoint returns `passwordHash`.
- There is no self-registration, password reset or refresh token in this sprint.

### 2.3 UI behaviour

**`/login`**

- Email and password fields with visible labels.
- Client-side validity checks show inline field messages, set `aria-invalid` and focus the first
  invalid field; server validation details use the same behavior.
- Client-side check for a non-empty email and password; server remains authoritative.
- Submit button disabled and spinner shown while the request is pending.
- `401` shows "Invalid email or password." in an alert banner with `aria-live`.
- Success stores the token, loads the current user and redirects:
  - `SURVEY_OWNER` → `/owner/surveys`
  - `RESPONDENT` → `/surveys`
- An expired or revoked token on any request clears the session and redirects to `/login`.
- `/` waits for the current-user check, then redirects authenticated users by role and unauthenticated
  users to `/login`, as specified in system SDS §3.1.

**Navbar**

- Shows full name and role.
- "Log out" calls the API, clears local state and redirects to `/login`.
- If the logout request fails, the client still clears local state; the server-side revocation is
  tested separately.

### 2.4 Data specification

Table `users`:

| Field | Type | Constraint |
|---|---|---|
| `id` | UUID | Primary key |
| `email` | text | Unique, stored lowercase |
| `password_hash` | text | bcrypt cost 10, `$2b$10$` prefix |
| `full_name` | text | 1–120 characters |
| `role` | enum | `SURVEY_OWNER` or `RESPONDENT` |
| `token_version` | integer | Default 0, incremented on logout |
| `created_at`, `updated_at` | timestamptz | Automatic |

No schema change is needed for RBAC beyond this table.

### 2.5 API specification

#### POST `/api/auth/login` (public)

Request:

```json
{ "email": "owner1@survey.local", "password": "Password123!" }
```

Success `200`:

```json
{
  "success": true,
  "data": {
    "token": "<jwt>",
    "user": {
      "id": "<uuid>",
      "email": "owner1@survey.local",
      "fullName": "Course Coordinator",
      "role": "SURVEY_OWNER"
    }
  }
}
```

Errors:

- `400 VALIDATION_ERROR` — missing or malformed email/password, with field-level details that never
  include submitted values, as specified in system SDS §4.5.
- `401 INVALID_CREDENTIALS` — unknown email or wrong password. The message is identical for both to
  avoid account enumeration; unknown emails still perform a bcrypt comparison against a fixed dummy
  hash so response timing does not expose whether an account exists.

#### GET `/api/auth/me` (authenticated)

Success `200`:

```json
{
  "success": true,
  "data": {
    "id": "<uuid>",
    "email": "resp1@survey.local",
    "fullName": "Student One",
    "role": "RESPONDENT"
  }
}
```

Errors: `401 TOKEN_REQUIRED`, `401 INVALID_TOKEN`, `401 TOKEN_REVOKED`.

#### POST `/api/auth/logout` (authenticated)

Success `200`:

```json
{ "success": true, "data": { "message": "Successfully logged out." } }
```

Side effect: `token_version = token_version + 1`.

Errors: `401 TOKEN_REQUIRED`, `401 INVALID_TOKEN`, `401 TOKEN_REVOKED`.

### 2.6 Acceptance criteria

| AC | Observable outcome |
|---|---|
| **AC-F01-01** | Valid credentials return `200`, a signed JWT and a user object without `passwordHash`. |
| **AC-F01-02** | A wrong password returns `401 INVALID_CREDENTIALS` and no token. |
| **AC-F01-03** | `GET /api/auth/me` with a valid token returns the id, email, full name and role stored in the database. |
| **AC-F01-04** | `POST /api/auth/logout` returns `200` and increments the user's `tokenVersion`. |
| **AC-F01-05** | A token used before logout returns `401 TOKEN_REVOKED` on the next protected request. |
| **AC-F01-06** | Every seeded password hash starts with `$2b$10$`; no plaintext password or hash appears in any API response. |
| **AC-F01-07** | Malformed login input returns `400 VALIDATION_ERROR` with field-level details and no submitted values. |
| **AC-F01-08** | Unauthenticated `GET /api/auth/me` and `POST /api/auth/logout` return `401 TOKEN_REQUIRED`. |
| **AC-F01-09** | A request to a role-protected route by the wrong role returns `403 FORBIDDEN_ROLE`. |
